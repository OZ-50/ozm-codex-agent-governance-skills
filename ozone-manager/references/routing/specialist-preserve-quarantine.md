# OZM Specialist Preserve And Quarantine

Load this file before routing to a non-OZM specialist or when a quarantined/experimental specialist is being considered.

OZM-first routing must not hide specialist skills. OZM owns workflow governance boundaries; validated specialists keep their domain authority after OZM freezes scope, owner, write-set, and claim ceiling.

All preserved specialists should carry an `OZM / GPT-5.5 Interop` block that states:

- OZM owns requirement load, dispatch freeze, write-set, truth owner, and claim ceiling
- the specialist owns only its domain judgment or execution surface
- GPT-5.5 or stronger models must ground conclusions in current evidence rather than fluent synthesis
- specialist outputs are candidate evidence until OZM/controller review raises the claim ceiling

## Frontend And Design Implementation Specialists

Use after OZM freezes write-set and verification target when the work surface is UI, UX, visual fidelity, Figma sync, screenshot iteration, or design-system quality.

- `ozm-ux-ui-expert-suite`
- `ui-ux-pro-max:data-backend` as an optional preserved local search backend, not a normal-path skill target
- `ui-ux-pro-max` as the preserved active backend id when the local skill shelf is available
- `figma-design-sync`

Default selection:

- `ozm-ux-ui-expert-suite`: default OZM UI/UX owner for web UI creation, modification, component work, landing pages, dashboards, app shells, screenshot-driven refinement, and visual implementation review.
- `ui-ux-pro-max:data-backend`: use only when the local heavy search/data backend is explicitly needed for product-type matching, style exploration, design-system recommendation, searchable UX rules, or icon/chart/font guidance.
- `figma-design-sync`: use when Figma is the active design truth and code must be reconciled to it.

Absorbed low-conflict donor rules from Impeccable, Taste Skill, Better Icons, and Motion AI Kit:

- read existing product/design context when present, but absence is not automatic authority to create new context files unless the user asks
- classify brand-facing surfaces separately from product/task surfaces before applying taste rules
- require screenshot, browser, Figma, or equivalent visual evidence before positive UX/UI completion claims
- treat icon choice as a real design surface: prefer existing project icon libraries, consistent stroke/fill, accessible labels, and tool-backed search over invented inline SVG
- treat motion as a state, feedback, hierarchy, or storytelling tool with a performance and reduced-motion budget; do not force GSAP, Motion, or image generation when the project does not already support or need them
- use anti-pattern audits as candidate findings, not as automatic permission to rewrite unrelated UI

When human UX tuning is part of the task, `ozm-ux-ui-expert-suite` owns domain analysis of the before/after design delta. Required posture:

- capture old design problem, human adjustment, intended user outcome, UX contract dimension, evidence, and scope
- preserve one-off preference and project-specific brand taste as local notes
- route repeated generic UX failures to the relevant specialist-skill hardening path
- route governance failures such as missing screenshots, stale Figma truth, skipped state verification, or claim overreach back to OZM

Do not let OZM turn visual taste into controller truth merely because human feedback repeated. OZM owns the promotion gate and claim ceiling; `ozm-ux-ui-expert-suite` owns the candidate design judgment.
